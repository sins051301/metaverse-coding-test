# pipeline — 문제 수집·변형·검수·업로드 파이프라인

> 상태: **1차 구현 완료 (2026-11-17)** — 프로그래머스 수집 → 변형 → 검증 → 검수 화면 → SQL 생성

## 실행 방법

```bash
cd pipeline
pnpm install
pnpm start          # http://localhost:4000
```

- 필요한 것: 로컬에 설치된 Chrome(Playwright 가 `channel: 'chrome'` 으로 사용), 실행 중인 Docker + `coding-test/judge-javascript` 이미지(`./gradlew buildJudgeImages`), 로그인된 `claude` CLI
- 포트 4000 은 프론트 개발 서버(3000)와 겹치지 않게 골랐다. `PIPELINE_PORT` 로 바꿀 수 있다
- `PIPELINE_MODEL=sonnet` 처럼 지정하면 변형에 쓸 모델을 바꾼다(기본은 CLI 기본 모델)
- `claude` 가 `.cmd` 래퍼라 셸 없이 실행할 수 없으면 래퍼가 가리키는 `claude.exe` 를 찾아 쓴다. 못 찾으면 `PIPELINE_CLAUDE` 로 경로를 지정한다

화면 사용 흐름: 문제 번호 입력 → `수집 + 변형` → (자동) 변형·검증 → 원본/변형본 비교, 겹치는 표현·검증 결과 확인 → `승인` 또는 `반려 후 재변형` → 승인된 문제가 생기면 `SQL 생성` → 생성된 `V{n}__add_problems_*.sql` 을 직접 확인·커밋

## 1. 목적

문제 은행을 채우기 위한 로컬 전용 도구.

```
프로그래머스(이후 코드트리)에서 문제 수집
→ claude -p 로 문제 변형
→ docker/judge 이미지로 정답 코드 실행·검증
→ 로컬 검수 화면에서 사람이 승인
→ 승인된 문제만 Flyway 마이그레이션 SQL 로 생성
```

## 2. 확정된 결정과 이유

| 결정 | 이유 |
|---|---|
| 로컬에서 실행 | 운영 서버에 크롤링·LLM 호출 부하와 비밀값을 올리지 않는다 |
| 변형은 `claude -p` 헤드리스 호출 (B안) | API 키 없이 Claude 구독 한도 안에서 돌아간다. 대화형(A안)과 달리 검수 화면의 반려 버튼으로 사유를 붙여 자동 재변형할 수 있다 |
| 검수 화면은 파이프라인 Node 서버 안의 단순 페이지 | 크롤링·변형·검증과 같은 프로세스라 버튼으로 바로 재실행할 수 있고, 운영 `frontend/` 와 완전히 분리된다 |
| 업로드는 Flyway SQL 파일 생성 | 운영 DB(3306)는 외부에 열지 않으므로 관리자 업로드 API와 관리자 인증이 필요 없다. 기존 배포 흐름으로 반영되고 문제 이력이 git 에 남는다 |

## 3. 저작권·약관 주의

프로그래머스·코드트리 약관은 콘텐츠 무단 수집·복제를 금지하고, 지문·테스트케이스는 저작물이다. 비영리 사이드 프로젝트라 위험을 감수하기로 했지만, 레포가 공개이므로 다음 세 가지를 지킨다.

1. **원본은 레포에 올리지 않는다.** 크롤링 원본과 작업본은 `workspace/` 에만 두고 `.gitignore` 로 제외한다. 레포와 DB 에는 변형 결과만 들어간다.
2. **확실하게 변형한다.** 단어 치환이 아니라 이야기 배경, 변수 이름, 예제, 제약 수치까지 바꾸고 알고리즘 구조만 남긴다. 검수 화면에서 원본과 겹치는 구간을 강조해 사람이 확인한다.
3. **요청 속도를 제한한다.** 요청 사이 2~3초 간격, 필요한 문제 수만 수집한다.

## 4. 구조와 흐름

### 폴더 구조

```
pipeline/
  src/
    crawl.ts       Playwright 로 원본 수집
    transform.ts   claude -p 호출 → 변형본 JSON
    crosscheck.ts  claude -p 한 번 더 호출 (지문만 전달) → 완전탐색·Java 풀이, 경계값, 작은 입력 생성기, 제한사항 검사기
    verify.ts      judge 이미지로 생성기·정답 코드 실행 → 기대 출력 생성 + 대조 검사
    publish.ts     승인된 문제 → backend/src/main/resources/db/migration/V{n}__add_problems_xxx.sql
    server.ts      검수 화면 + 위 단계를 버튼으로 실행하는 API
    prompts/transform.md
    prompts/crosscheck.md
  public/          검수 화면 (HTML 1장 + JS)
  workspace/       전부 .gitignore
    raw/<출처>-<원본id>.json
    drafts/<id>.json
```

### 단계별 동작

1. **crawl**: 프로그래머스 문제 URL 또는 번호 목록을 받아 지문, 제한사항, 입출력 예, 파라미터 이름을 `workspace/raw/` 에 저장한다. 코드트리는 페이지 구조 확인 후 두 번째 출처로 붙인다.
2. **transform**: 문제마다 `claude -p` 를 한 번 실행해 다음을 JSON 으로 받는다.
   - 새 제목·지문(배경·변수명·수치 변경), `level`, `parameters`, `returnType`
   - 정답 코드 (JavaScript)
   - 예제 입력 3~5개 + 테스트 입력 생성기 코드(경계값 + 큰 입력)
   - 반려된 문제는 반려 사유를 프롬프트에 붙여 다시 실행한다
   - 도구 사용(파일 쓰기·명령 실행)은 끄고 텍스트만 생성하게 한다
3. **crosscheck**: `claude -p` 를 한 번 더 실행한다. **정답 코드는 보여 주지 않고 변형된 지문만** 준다(6장 "대조 검증").
4. **verify**: 생성기로 입력을 만들고, 정답 코드로 기대 출력을 만든 뒤 6장의 검사를 수행한다.
5. **review**: 검수 화면
   - 왼쪽 원본, 오른쪽 변형본 지문(마크다운 미리보기 + 직접 수정)
   - 원본과 5단어 이상 똑같이 이어지는 구간 강조
   - 테스트케이스 표(예제/히든, 입력·기대 출력 일부), 정답 코드
   - 버튼: `승인` / `반려(사유 입력 → 재변형)` / `다시 검증`
   - 반려하면 직전 검증 오류(대조 불일치 반례 포함)가 반려 사유에 자동으로 붙어 재변형 프롬프트에 들어간다
6. **publish**: `approved` 문제를 모아 기존 `V2__insert_seed_problems.sql` 과 같은 형식(`problems`, `problem_parameters`, `test_cases` INSERT)으로 다음 버전 Flyway SQL 을 만든다. 커밋은 사람이 한다.

### draft 상태 흐름

```
transformed ──verify──> verified ──review──> approved ──publish──> (SQL 파일)
     ▲                     │                    
     │                     └──review──> rejected ──(사유 첨부 재변형)──┐
     │                                                              │
     └──────────────────────────────────────────────────────────────┘
transformed ──verify──> failed ──(재변형 또는 다시 검증)──> transformed
```

## 5. judge 이미지 재사용

- 백엔드를 띄우지 않고 `docker/judge` 이미지를 `docker run` 으로 직접 실행한다.
- 입력: `/judge/in` 에 소스 파일(`solution.js`)과 `tests/*.in`(인자 JSON 배열)을 넣는다.
- 출력: 결과 tar 의 테스트별 `.out` 에 담긴 `{"returnValue":..., "userOutput":...}` 에서 `returnValue` 를 기대 출력으로 쓴다.
- 격리 옵션은 `SandboxRunner` 와 같게 준다(네트워크 차단, 읽기 전용, 권한 제거, 메모리·CPU·프로세스 수 제한).
- **정답 코드는 JavaScript**: 컴파일 단계가 없어 검증이 빠르다.
- **생성기도 같은 샌드박스에서 실행**: LLM 이 쓴 코드이므로 로컬 Node 로 직접 실행하지 않는다.
- **기대 출력은 LLM 이 쓰지 않는다**: LLM 이 손으로 적은 기대 출력은 자주 틀린다. 정답 코드를 실제로 실행한 결과를 쓰면 지문·정답 코드·테스트가 서로 일치하는 것이 보장되고, 남는 위험은 "정답 코드 자체가 틀린 경우" 하나로 줄어 검수에서 그 부분만 보면 된다.

## 6. 검사 항목

- 모든 테스트가 문제의 시간 제한(`time_limit_ms`) 안에 끝나는지
- 반환값이 `returnType` 과 맞는지. `returnType`·파라미터 타입은 기존 CHECK 제약에 있는 타입만 허용: `int`, `long`, `double`, `boolean`, `String`, `int[]`, `long[]`, `String[]`, `int[][]`
- 테스트케이스 크기 상한. 큰 JSON 행을 정렬하다 MySQL `Out of sort memory` 가 난 적이 있어(README 8장) 입력·기대 출력 크기를 제한한다
- 예제 입력의 결과가 변형된 지문의 입출력 예 표와 일치하는지
- `problems.id` 는 AUTO_INCREMENT 가 아니므로 publish 단계에서 기존 마이그레이션의 최대 id 다음 번호를 직접 지정한다

### 대조 검증 (2026-11-17 추가)

변형본의 예제·히든 테스트·정답 코드는 원본에서 오지 않고 전부 Claude 가 새로 만든다. 히든 테스트의 기대값은 정답 코드 실행 결과이므로, **정답 코드가 틀리면 히든 테스트도 함께 틀리고** 예제 2~5개만으로는 이를 잡지 못한다. 그래서 같은 지문을 독립적으로 푼 결과와 대조한다.

| 단계 | 대상 입력 | 실패 조건 |
|---|---|---|
| 제한사항 검사기 (`validator`) | 예제 + 생성 + 경계 + 작은 입력 전부 | 지문 제한사항을 어긴 입력이 하나라도 있음 |
| 정답 코드 실행 | 전부 | 에러·시간 초과·타입 불일치, 예제 기대값과 다름 |
| 완전탐색 대조 (`bruteSolution`) | 예제 + 경계 + 작은 입력(200~400개) | 정답 코드와 결과가 다름. 작은 입력에서 완전탐색이 실패해도 실패. 큰 경계 입력에서 5초 안에 못 끝나면 그 케이스만 생략 |
| Java 대조 (`javaSolution`) | DB 에 저장할 테스트(예제 + 생성 + 경계) | 결과가 다름, 런타임 에러(입력이 `int` 범위를 넘으면 래퍼의 `Math.toIntExact` 에서 에러). 시간 초과는 경고 |

- **독립성**: 대조 자료를 만드는 호출에는 정답 코드를 보여 주지 않는다. 보여 주면 같은 잘못된 해석을 따라가서 대조가 의미 없어진다. 지문만 보고 짜므로 **지문이 모호해도** 불일치로 드러난다.
- **완전탐색은 지름길 금지**: 그리디·DP 점화식·공식처럼 증명이 필요한 방법을 쓰지 말고 규칙을 그대로 시뮬레이션하라고 지시한다(`prompts/crosscheck.md`).
- **경계값**: 변형 프롬프트(`prompts/transform.md`)의 생성기 규칙과 대조 프롬프트의 `boundaryCases` 양쪽에서 제한사항을 한 줄씩 짚어 최소·최대·같은 값·답이 0·이상/초과 경계를 반드시 넣게 한다. 경계 케이스는 히든 테스트로 함께 저장한다(최대 15개).
- **작은 입력은 저장하지 않는다**: 수백 개를 저장하면 제출마다 테스트 프로세스를 수백 번 띄워야 해서 채점이 느려진다. 대조에만 쓴다.
- 비용: 문제당 `claude -p` 1회 추가.

## 7. 기술 선택 (2026-11-17 승인)

| 항목 | 선택 | 이유 | 대안 |
|---|---|---|---|
| 언어 | TypeScript, 빌드 없이 `node` 로 바로 실행 | 로컬 Node 22.23 은 타입 제거(type stripping)가 기본으로 켜져 있어 tsc·번들러 설정이 필요 없다 | 순수 JS |
| 서버 | 내장 `node:http` | API 가 대여섯 개뿐이라 프레임워크가 필요 없다 | Express, Hono |
| 크롤링 | Playwright | 이전 프로젝트(resume-autofill)에서 사용 경험이 있고, 코드트리가 JS 렌더링 페이지일 가능성에 대비 | fetch + cheerio (가볍지만 JS 렌더링 페이지는 못 읽음) |
| 검수 화면 | HTML 1장 + 순수 JS, 마크다운은 `marked` | 로컬 도구라 React 는 과하다 | 기존 `frontend/` 재사용 (제외하기로 결정) |
| 패키지 매니저 | pnpm | `frontend/` 와 통일 | — |

## 8. `claude -p` 호출 옵션과 이유

기본 옵션으로 호출하면 Claude Code 의 기본 시스템 프롬프트·MCP 도구 설명·사용자 메모리가 함께 실려 **한 번에 입력 약 16만 토큰**이 들었다. 아래 조합으로 **약 1천 토큰 + 프롬프트**로 줄였다(2026-11-17 측정).

| 옵션 | 이유 |
|---|---|
| `--system-prompt "..."` | 기본 시스템 프롬프트를 짧은 출제자 지시로 교체 |
| `--tools ""` | 파일 쓰기·명령 실행 등 도구를 모두 끈다. 텍스트만 생성 |
| `--strict-mcp-config` | `--mcp-config` 없이 쓰면 MCP 서버를 하나도 불러오지 않는다 |
| `--disable-slash-commands` | 스킬 목록을 싣지 않는다 |
| `--setting-sources project` | 사용자 설정(전역 CLAUDE.md 등)을 싣지 않는다 |
| `--no-session-persistence` | 세션 기록을 남기지 않는다 |
| `--output-format json --json-schema <스키마>` | 결과가 `structured_output` 필드에 스키마대로 들어온다 |

`--bare` 는 컨텍스트를 가장 많이 줄이지만 API 키 인증만 받아서 구독 로그인으로는 쓸 수 없다.

## 9. 구현 메모

- 작업은 대기열 하나로 순서대로 처리한다. `claude -p` 와 Docker 컨테이너를 동시에 여러 개 띄우면 노트북 메모리가 부족해지기 때문이다
- 생성기는 judge 이미지의 래퍼를 그대로 쓰기 위해 `solution()` 이 테스트 입력 배열을 return 하는 형태로 받는다. 인자 `[]` 로 한 번 실행하면 `returnValue` 가 곧 입력 목록이다
- 크롤링은 `?language=java` 페이지에서 지문(`.guide-section-description .markdown`)과 Java 시작 코드(`textarea#code`)를 읽는다. 시작 코드의 시그니처로 파라미터·반환 타입을 정확히 알 수 있다
- publish 는 기존 마이그레이션 파일들에서 최대 버전과 최대 `problems.id` 를 읽어 다음 번호를 정한다
